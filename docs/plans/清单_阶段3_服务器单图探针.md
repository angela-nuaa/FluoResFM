## 2. 云端传输与目录布局

目标：把探针脚本、2 个配置、计划/清单文档与 napari-fluoresfm 源码（含 `.git`）推送到云端个人目录；权重与数据只读、一次性同步。

云端目录布局（个人 `lc` 目录，与本地一致）：

- `configs/biosr_mt_fluoresfm_server_probe_20260805_s{1,2}.json`
- `scripts/probe_biosr_mt_fluoresfm_server.py`、`scripts/sync_probe_to_server.py`
- `docs/plans/计划_BioSR-MT全目录严格生产.md`、`docs/plans/清单_阶段3_服务器单图探针.md`
- `repos/napari-fluoresfm`（含 `.git`，保持 `2fded7c`；s1 对照时再 checkout `d623403`）
- 权重（必传，约 3.35 GB）：`example/checkpoints/fluoresfm/epoch_0_iter_700000.pt`、`example/checkpoints/biomedclip/open_clip_config.json`、`example/checkpoints/biomedclip/open_clip_pytorch_model.bin`（`desktop.ini`/`.cache` 不上传）
- 探针最小数据（约 2 MB）：`test/channel_0/WF_noise_level_3/41.tif` 与 `WF_noise_level_3_fluoresfm/41.tif`
- 批量阶段才需要：完整 `example/data/BioSR_MT`（83,591 文件，约 1.54 GB）

一键同步（优先 WSL rsync，回退 OpenSSH scp；凭据走 ssh-agent/交互输入，不入库）：

```bash
python scripts/sync_probe_to_server.py --host <主机> --user <账户> --dry-run             # 预览命令与传输工具
python scripts/sync_probe_to_server.py --host <主机> --user <账户> --include-probe-data  # 单图探针最小集（约 3.4 GB）
python scripts/sync_probe_to_server.py --host <主机> --user <账户> --include-data        # 完整 example（约 4.9 GB）
```

要点：

- 无需预先打包压缩：rsync `-z` 在传输时压缩、远端落盘保持原字节，SHA-256 与本地一致；权重为浮点二进制，预压缩收益极低。
- 远端目录只允许个人目录（默认 `~/lc/FluoResFM`），脚本只推送、不删除远端内容。
- 若云端不便接收 `.git`，可改用云端 `git clone` + checkout `2fded7c`，但须另行核对 `git rev-parse HEAD`。
- 传输后、正式推理前，先在云端 `--dry-run` 复核一次。

## 6. 执行

先跑首选新版本 s2：

```bash
cd "$WORKSPACE"
python scripts/probe_biosr_mt_fluoresfm_server.py \
  --config configs/biosr_mt_fluoresfm_server_probe_20260805_s2.json \
  --workspace-root "$WORKSPACE"
```

若需老版本对照 s1（先 checkout `d623403`）：

```bash
cd "$WORKSPACE"
python scripts/probe_biosr_mt_fluoresfm_server.py \
  --config configs/biosr_mt_fluoresfm_server_probe_20260805_s1.json \
  --workspace-root "$WORKSPACE"
```

先以 `--dry-run` 校验输入与源码版本预期；`--dry-run` 不写任何输出、不加载 Torch。

退出码语义：

| 退出码 | 含义 | 后续动作 |
| ---: | --- | --- |
| `0` | 严格一致（文件 SHA-256 相同） | 可进入阶段 3.3 批量生产规划 |
| `1` | 仅数值等价（float32 容差 `1e-6` 内） | 不得视为严格一致；记录差异来源，继续排查 |
| `2` | 比较失败（shape/dtype 不一致或超差） | 停止，保留运行目录与日志 |
| `3` | 运行/准备错误（缺输入、源码版本不符、CUDA 不可用、上游异常） | 读取 `failure.json` 定位原因 |

产出文件（均在新运行目录内）：

- `probe_input/`：仅含单张输入的隔离目录（复制后校验哈希）。
- `candidate/`：固定版本上游推理输出。
- `input_index.txt`：单行输入索引。
- `environment.json`、`pip_freeze.txt`：环境冻结。
- `run.log`：上游推理 stdout/stderr。
- `comparison.csv`：逐文件 shape/dtype/最大/平均绝对误差/双 SHA-256/状态。
- `manifest.json`：机器可读总记录（含源码树摘要、权重与输入哈希、参数、环境、判定）。
- `run.md` 或 `failure.json`：人类可读总结或失败原因。

## 7. 判读与验收

- 每文件状态为 `strict`（shape、dtype、数组内容与文件 SHA-256 均一致）、`numerically_equivalent`（仅在预声明 float32 容差内一致）或 `failed`。
- 只有 `strict` 才能支撑“该生成链严格复现参考文件”的结论。
- `numerically_equivalent` 或 `failed` 均不得进入批量生产；不得以视觉近似或最小误差候选替代严格判定。
- 关闭 `torch.compile` 的结果仅用于隔离变量，不得默认等价于历史输出；历史行为必须以 `compile=true`、兼容环境验证。

## 8. 停止条件与失败处理

- 历史生成时的 Torch、Triton、CUDA、模型源码、prompt 或 compile 行为任一项不同，都可能使推理 TIFF 不一致；不能由近似视觉结果推断严格成功。
- 任一探针失败时保留独立候选目录与日志，禁止删除参考、覆盖旧证据或以失败候选替代 bundled example。
- 若多个候选链均不通过，报告“无法在现有证据下严格生产”，而不是选择误差最小的候选。
